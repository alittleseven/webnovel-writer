# 03 · 批判性思考（八轮）

> 方法：每轮先立「靶子」（本方案或输入线的一个立场），再尽力击穿它，最后给出裁决与方案修正。批判不通过的方案不配动工。
> 轮一至轮八按依赖顺序排列；每轮结论已回写进 01/02/04/08 对应章节。

## 轮一 · 载体与双真源批判：「A 线说不跟随 v7，你凭什么推翻？」

**靶子**：A 线方案（2026-09-02）明确「不跟随 v7 数据模型（book.yaml/决策卡/settle 不引入）」，理由是当时 v7 是未验证的重构。本方案却把 v7 story-repo 当底座。

**击穿过程**：
1. A 线成文时（09-02 之前）v7 写路径确实未实跑；但此后 48 小时内事实变了——v7.0.0 已发版，第 37/38 章经 v7 链路实写落定（`loom-books/fantasy01` 的 settle 记录），「派生物可丢弃」「settle 原子性」「决策卡-机检-作者验收」链路验证通过。决策依据消失，决策应更新。
2. 反向风险：若沿用 A 线「v6 目录契约」，等于让本仓（已 v7.1.0）回退，或维护两套书仓格式——**双真源是数据治理的头号反模式**。
3. 但 A 线警惕 v7 的一点仍然成立且必须吸收：v7 的「定稿只增不改」与作者主权的「作者可改一切」冲突。v7 settle 语义是为 AI 写入设计的（防 AI 篡改已定稿），不是为作者设计的。

**裁决**：以 v7 story-repo 为**格式底座**，但把「作者修改权」注入其语义层——①作者对 `定稿/` 的修改是合法操作，走 journal+retcon 记录而非被禁止；②AI 仍受 settle 纪律约束；③`.story-system/` 合同树从「真源」降级为「编译产物」（由 大纲+素材定版+设定 编译生成），消灭「合同 vs 大纲」双真源。A 线的六域目录契约（作者只碰四处）映射到 v7 布局上实现（见 05）。

## 轮二 · 打扰频率批判：「一切以作者为主 = 把作者淹死在确认里」

**靶子**：需求 N2-N7 每条都有「作者可修改/确认/固定」，字面执行 = 每个生成物都要作者点一次头。300 章的书要写 300 份章纲确认、几十次素材裁决——作者会直接绕过系统手写文件，治理层整体失效。

**击穿过程**：
1. 区分两类动作：**创作决策**（总纲方向、卷冻结、素材采纳——低频高价值，值得停下来）与**机械流转**（留账、stale 标记、轨迹写入——高频零价值，不该见作者）。
2. 确认成本必须随阶段边界聚合：章纲一批 8 张一次确认；素材归纳一卷一次 material-review；不是逐条弹窗。
3. 默认档位设计：AI 提案在作者**不反对时即按提案推进但保留画廊可回溯**（草稿区公民），只有「冻结/采纳进定版」是显式动作。反转「先确认再生成」为「先生成可回溯，冻结时才确认」。

**裁决**：确认面收敛到四个显式动作——`regen 采纳`、`卷冻结`、`定版修改裁决`、`settle（写作链已有）`。其余全部后台留账。作者被打扰的频率 ≈ 每卷 3-5 次。（已写入 P1/P5 与 07 各流程。）

## 轮三 · 冻结悖论批判：「300 章的书，总纲一定会改」

**靶子**：「分阶段固定」的字面语义是锁定。但商业网文的现实是：写到 150 章发现主线要调、配角要扶正、战力天花板要抬——**锁死总纲等于逼作者绕过系统**，而绕过一旦发生，留账/影响分析全部失真。

**击穿过程**：
1. 冻结的真正用户价值不是「防改」，是「改的时候知道会伤到哪」：第 200 章改了第 1 卷定下的金手指规则，哪些章的描写需要 retcon？没有定版快照与使用轨迹，这个问题无法回答。
2. 因此冻结 = **建立可反查的依赖快照**，而非建立锁。锁是副作用，且是有害副作用。
3. retcon 必须事务化（loom 已有先例）：`retcon(N)` 事件 + 影响清单 + 修改执行 + 账本同步，一个 git commit 收口。

**裁决**：P4 原则——冻结=变更走影响分析。定版修改三选项（只改今后/全书 retcon/放弃）由 `impact` 命令产出建议、作者选择。（已写入 06 §状态机、07 F-07。）

## 轮四 · 素材失控批判：「可成长的素材库 = 慢性上下文癌症」

**靶子**：素材随章节增长、AI 归纳不断追加——按 300 章 × 每章沉淀 2-3 条估算，活层将积累 600-900 条，检索噪声、版本矛盾、上下文预算三重爆炸。且上一轮质量审阅已证明：上下文预算工程在饱和时**最先牺牲的恰是文风层**（F-04）。

**击穿过程**：
1. 无淘汰的成长不是成长是堆积。素材必须有生命周期：使用轨迹是淘汰依据（N 卷未用 → 降权/归档建议）、material-review 是淘汰时机（每卷一次）、作者裁决是淘汰闸门。
2. 上下文装配只允许**定版层 + 活层精选（按本章实体相关性 top-K）**，全量素材永不进上下文——这是硬边界，不是建议。
3. 矛盾检测：同 key 素材新旧版本并存时，装配器只认「活层最新 + 定版快照」二元组，历史版本只存于 git。

**裁决**：三层模型（活/定版/轨迹）+ material-review 淘汰 + 装配硬边界 + 与 W5（DROP_ORDER 重排）联动。（已写入 06 §素材卡、07 F-05/F-06、08 M2。）

## 轮五 · 战力数值化陷阱批判：「把力量体系做成数值表，书就会有游戏感」

**靶子**：B 线 A2 要求「战力体系确定性化」。字面执行 = 境界/战力全数值化、战斗按数值裁决——网文的越级挑战、以弱胜强、天时地利人和将全部失去叙事空间，作者想象力被数值表反杀。

**击穿过程**：
1. 网文战力的本质是**叙事规则**（境界压制有例外、代价可换强度、相性可翻盘），确定性应该落在「规则的执行一致性」而非「结果的数值比较」。
2. 但纯叙事化又回到现状老路：越级取胜无账可查、战力通胀无感知。需要的是**双层结构**：叙事层（公理/代价/克制，作者自由）+ 锚点层（境界序、已发生战例的胜负与依据，机器可查）。
3. 校验器只对锚点层做硬检查：①越 N 阶取胜必须能列出依据（金手指/代价/外因——数据里必须存在对应条目）；②通胀监控只做曲线对账（主角战力跃升 vs 卷纲里程碑规划），提示不阻断。

**裁决**：双层战力模型。锚点层 schema 见 06 §8；校验语义见 07 F-09。绝不生成「战斗力数值」。fantasy01 的 `力量体系.md`（公理/境界链/晋级条件/越级代价/战斗规则分节）已是正确形态的半结构化先例，在其上抽锚点即可。

## 轮六 · 想象力悖论批判：「AI 帮你想设定，越帮越没得想」

**靶子**：设定工坊生成「完整的境界体系/功法/法宝」——AI 想得越完整，作者的创作空间被挤压得越小；且 AI 设定同质化（训练数据偏好），采纳越多书的独特性越差。这是对 N8 需求本身的批判。

**击穿过程**：
1. 区分两类设定工作：**体系骨架**（境界阶梯、代价框架——工程问题，AI 生成有价值）与**灵魂设定**（核心金手指、世界观反差、主角独特性——创作问题，AI 代劳有害）。
2. 工坊的输出物应该是「**概念组合提案**」：跨域概念拼接（例：把「纸质档案管理」×「修仙藏经阁」×「记忆可被篡改」拼出新的金手指方向）+ 反差钩子清单，而不是成品体系文档。
3. 防同质化机制：提案必须标注「与既有设定的差异点」与「市面常见度自评」；采纳率过低（作者连续不采纳）是工坊提示词需要进化的信号（进入学习闭环）。
4. 「生成即登记」防爆炸：只有作者采纳的提案才登记进设定集；未采纳提案保留在画廊 N 卷后清理。

**裁决**：工坊四生成器（境界/功法技能/法宝丹药/命名风格）全部改为「提案模式」，输出到 regen 画廊；采纳才登记（设定集+锚点+合同三处同步）。（已写入 07 F-08。）

## 轮七 · 多计划冲突批判：「现在有几张路线图？」

**靶子**：本方案之前已存在三张活跃路线图——A 线 P0 实施计划（待裁决）、质量审阅 W1-W10、loom v3.0 的 P0-P5。加上本方案就是四张。四张图各自排期 = 没有图。

**击穿过程**：
1. 冲突检测：A 线 P0（author-sync/journal/目录契约）与本方案 M0 完全重叠——必须声明吸收关系，否则两个实现队；质量 W1-W3（写链增强）与 M5 重叠——同样；loom P0-P5 是**另一个工具仓**（projects/loom）的计划，工具不同但书仓格式理念重叠（loom-1 vs v7），若 loom 线继续演进会再造一个「织机版 fantasy01」。
2. 资源现实：单作者单维护者，串行队列是既有纪律（AGENTS.md/ADR 均确认）。四线并行必然全线烂尾。

**裁决**：①本方案 08 实施计划是**唯一总队列**，A 线 P0 与质量 W1-W10 被吸收（映射关系在 08 §0 声明）；②loom 线定位为**姊妹实验仓**，其可取成果（retcon 事务、文风域设计、素材工作台交互）以「设计借鉴」进入本方案，不在本仓实现 loom-1 格式；③每次质量/主权类新审阅产出后，必须并入总队列而非另开新图——本方案自身也遵守此纪律（未来修订走本文档版本化）。

## 轮八 · 宿主依赖批判：「押注 ZCode，万一换宿主呢？」

**靶子**：本方案宗旨写明「ZCode + webnovel-writer」。但多宿主 ADR（本仓 2026-09-02）刚确立「ZCode 是首期宿主，adapter 模式不锁死」。方案若把治理逻辑做进 ZCode 专有面（hooks/MCP/命令），换宿主即重写。

**击穿过程**：
1. 拆解治理层的宿主耦合面：author-sync 的扫描/分类/留账是纯 git+文件操作（宿主无关）；「会话启动自动跑」才是宿主面（hook）；「作者看到影响报告」也是宿主面（skill/命令）。
2. 正确分层：**内核**（新 CLI 命令全部走 `webnovel.py`，任何终端可跑）+ **宿主壳**（hook 触发、skill 编排、MCP 只读工具、命令入口——薄层，丢失可重建）。
3. 反向校验：ZCode 面带来的独特增益（userConfig 配置、MCP 结构化查询、`/webnovel:*` 入口）确实提升体验，值得做——但每个宿主面功能必须在内核有 CLI 等价物。

**裁决**：P7 原则落为硬规则——**每个新功能先有 CLI 实现，再有 ZCode 壳**；MCP 工具全部只读且是 CLI 的薄包装（上一任务 MCP server 的 adapter 模式延续）。验收含「无 ZCode 环境下全流程可跑」冒烟。

## 批判总结：方案被这八轮改变了什么

| 轮 | 改变 |
|----|------|
| 一 | 底座定为 v7 story-repo；`.story-system/` 降级为编译产物；作者对定稿的修改合法化（journal+retcon） |
| 二 | 确认面收敛为四个显式动作；提案默认「生成可回溯」而非「先确认再生成」 |
| 三 | 冻结语义改为影响分析门；定版修改三选项裁决；retcon 事务化 |
| 四 | 素材装配硬边界（定版+活层精选）；material-review 淘汰机制 |
| 五 | 战力双层模型；锚点层才硬校验；不出数值表 |
| 六 | 工坊提案化（零件+反差钩子，不出成品）；采纳率进学习闭环 |
| 七 | 本方案为唯一总队列；A 线/质量线被吸收；loom 定位设计借鉴 |
