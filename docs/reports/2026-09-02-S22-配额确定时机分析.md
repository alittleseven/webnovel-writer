# S22 · section 配额应该在何时确定（分析报告）

> 队列：[单线执行队列 S22](../plans/2026-08-30-v7-单线执行队列.md)（2026-08-30 Human 指示置于最末：「届时分析配额的确定时机与方式……结论基于多本书的 D1 实测数据再下」）
> 前置分析：[S1 预算配额分析](2026-08-30-S1-预算配额分析.md)；本报告只下结论与指向，**不含实施**。

## 1. 结论（TL;DR）

1. **四选项的答案不是单选，而是分层**：默认值 = 构建期静态（维持现状）；按书调整 = 书构建期一次性预填（init/迁移时，数据源 = 书史统计而非 D1）；按题材默认 = 不采纳；运行期 = 只做丢弃降级（DROP_ORDER，已有），不做配额重定。
2. **队列注记的数据前提不成立**：D1 至今只有 fantasy01 一本书的数据，且 meter 结果仅保留最后一章、无历史归档。「多本书数据再下结论」的诚实结论是：**静态默认在单书现实下就是最优解**，按书/按题材校准在第二本真实书进入 v7 链路之前都属过度拟合。
3. **修订触发条件（替代「多本书 D1 归档」）**：第二本书 v7 链路写出 3-5 章后，比对其包内 section 实际占用分布——占用率持续 >90% 的节或 <10% 的节，才是需要动的配额。D1 量的是消耗（token 花费），不是 section 需求（上下文体量），**用它驱动配额校准是间接且失真的**；书史字数统计（已有 `book_word_stats`）与包占用统计才是直接信号。
4. 实施动作（book.yaml 覆盖入口 + init/迁移预填）**未排期**，待 Human 决定是否入队（§5）。

## 3. 经验数据盘点（单书三条链）

| 数据点 | 体积 | 对总预算占用 | 来源 |
|---|---:|---:|---|
| v6 load_context 优化前（ch35） | 59,977 字符 | 300% | S1 §1 |
| v6 load_context 预算后（ch35） | 19,241 字符 | **96%** | S1 §4 |
| v6 extract-context（ch36，S2 后） | 17,304 字符 | 87% | 队列 S2 |
| 设定 L0 摘要（ch36，S3） | 601 字符 | — | 队列 S3 |
| **v7 包（ch37）** | **2,691 字符** | **13.5%** | 实测 |
| └ 节级：决策卡 360/2,000（18%）、前情摘要 551/1,200（46%）、本章实体 393/3,000（13%）、**上一章结尾 1,207/1,200（101%，已触顶）**、书级元信息 144/500（29%） | | | 实测 |

三条观察：

1. **同一 20,000 默认值在两条链上的占用率 96% vs 13.5%**——总预算的真实约束力取决于链路结构，不取决于数值本身；v7 的决策卡+摘要+名册结构天然小于 v6 的全量投影结构。总预算「按书校准」的杠杆远小于「按链分层」。
2. **节级配额比总预算更早绑住**：v7 包总占用 13.5% 时，上一章结尾节已触顶（1,207/1,200）——「何时确定」的问题在节级比在总预算级更真实。
3. **书史字数与声明值脱节已有实例**：book.yaml 每章目标字数 5,000（作者声明）vs 书史均值 2,680——S19 机检因此用书史实绩校准而非声明值。**这证明「按书校准」在本项目已有成功先例（机检下限），可平移到配额**；但注意机检校准用的数据源是定稿正文（书史统计），不是 D1。

## 4. 四选项分析

评估准则：①冷启动可用（新书/迁移仓无数据时）②漂移风险（配额过紧砍硬约束=覆盖红线；过松=token 浪费）③机制成本（代码路径+测试+文档）④可观测可回滚 ⑤数据前提。

### A 构建期静态默认（现状）

- ①✓（常量对所有书可用）②单书下最优，跨书有风险但风险可被 ④ 捕获 ③✓ 零新增（现状即此）④ budget_used_tokens 真值 + 节级截断标记「…（预算截断）」在包内可见 ⑤ 单书数据即全部前提。
- **判定：维持为基线。** 在第二本书出现前，改它的任何替代方案都是在拟合一本半虚拟的书。

### B 按书校准

- 数据源三个候选：书史字数统计（**已有**，`book_word_stats`，settle/决策卡在用）、合同体积统计（迁移/init 时可算，无现成接口）、D1 计量（**无历史归档**，且量纲错位——见 §1.3）。
- 时机候选：init/迁移时一次性预填；或每章 settle 后滚动更新。滚动更新的收益可疑：同一本书第 5 章到第 40 章的合同结构基本稳定，配额不该频繁漂移，反而制造不可复现的上下文（同章重跑包不同）。
- **判定：采纳「书构建期一次性预填 + 静态默认兜底」形态**。落点建议 book.yaml（`context_budget:` 节，总预算 + 节配额均可覆盖），迁移器/init 时按书史字数与合同体积预填；不采纳滚动更新。

### C 按题材默认

- 题材影响的是**内容侧重**（悬疑的伏笔密度、爽文的爽点节拍），不是上下文**体量**；体量由合同结构与章字数规模决定，二者都不是题材函数。题材画像本身已有独立上限（genre_profile 1,500）。14 类题材 × 6-12 节的默认值矩阵 = 84-168 个无数据支撑的常数。
- **判定：不采纳。** 伪精确，维护成本高，无数据前提。

### D 运行期动态

- 现状已含其正确形态：DROP_ORDER 按价值递减丢弃 = 运行期降级，budget_used_tokens = 运行期可观测。**丢弃发生在截断配额之内**（先节配额、后总预算丢弃），运行期从不「确定」配额、只做「取舍」。
- 完全动态（按需求自适应调整配额）与项目原则冲突：确定性动作下沉 scripts、行为可测试、失败模式可预测。动态配额三者全失。
- **判定：只作为降级机制（已有），不作为确定机制。** 唯一值得加的是告警：包占用 >90% 或节级截断命中时在 stats 里留痕（现已有截断标记，差一个汇总信号），供「是否需要重校准」判断——实现成本低，可与 B 一起做。

## 5. 实施指向（未排期，待 Human 决定是否入队）

若采纳 §1.1 的分层结论，实施是一个 Bounded 档任务：

1. `book.yaml` 增加 `context_budget:` 可选节（总预算 + 节配额覆盖）；v6 `load_context` 与 v7 `build_context_pack` 读取（缺省 = 现有静态默认，零行为变化）。
2. 迁移器/init 预填：按书史字数（`book_word_stats` 同源口径）与合同体积一次算出写入；新书（<3 章）不预填，用静态默认。
3. 截断/占用汇总信号进 pack stats（v7）与 budget_used_tokens（v6）。
4. 测试：覆盖读取优先级（book.yaml > 常量）、缺省零变化、预填口径。

**修订触发条件**（关闭本分析的唯一悬置）：第二本真实书 v7 链路 3-5 章的包占用分布可得时，按 §1.3 复核静态默认是否仍成立——**不需要**为触发它先建 D1 历史归档。
