## 1. 现状诊断：每章 750 万 token 是怎么烧掉的

实测基线（作者 2026-08 口径）：**每章约 750 万 tokens，成本 1-2 元**（宿主：Claude Code / ZCode 均同量级）。

诊断结论：**不是某个单一巨型文件，而是三个因子相乘**。单独看每个注入物都不致命，乘上「对话历史逐轮全量重发」与「缓存失效重读」后就变成 750 万。

### 1.1 因子一：主代理对话累积 × 无预算的 CLI 大输出

主代理跑完 `/webnovel-write` 全程约 35-60 次工具往返，会话历史只增不减，其中三次 CLI 把「大 JSON 全文」直接打进对话，此后每一轮都重复计费：

| 命令 | 注入内容 | 量级（估算） | 证据 |
|---|---|---|---|
| `write-gate --stage prewrite --format json` | `story_runtime` = 4 份合同全文 + latest_commit（最多 2 份）+ 校验详情，indent=2 | 3-15k | `write_gates/prewrite.py:130` |
| `review-pipeline` | 审查结果 + 指标全量 payload | 2-5k | `review_pipeline.py:215` |
| `chapter-commit` | 完整 commit payload，内嵌 4 份 artifact 全文 | 3-10k | `scripts/chapter_commit.py:39` |

主代理会话稳态体积 30-80k tokens；70 轮 × 平均 60-100k ≈ **4-7M tokens**，是最大乘数。

### 1.2 因子二：同一信息多份复制注入

| 重复项 | 份数 | 位置 | 单章浪费（估算） |
|---|---|---|---|
| 4 份合同全文 | ×2 | `memory_contract_adapter.py:163-164`（`story_contracts` + `runtime_status` 再嵌一遍） | 5-20k/次调用 |
| commit payload | ×3-4 | `runtime_status` 内、独立 `latest_commit`、（accepted 时再 +1） | 同上 |
| 审查结果 JSON | ×3 | reviewer 回传 → 主代理 Write 落盘（`SKILL.md:136` 一带，reviewer 不持 Write）→ review-pipeline stdout 再打印 | 3-9k |
| 章纲 + 近章摘要 | ×2 | extract-context 降级路径顶层与 `core.*` 重复（`extract_chapter_context.py:325-333 vs :352`）；load-context 的 memory_pack 内又一份 | 2-5k |
| 正文全文 | ×3 读 | 主代理 Write → reviewer Read → data-agent Read，polish 再多次 Edit | 8-12k |
| memory_pack 内部 | ×1.5-2 | `long_term_facts`=`semantic_memory` 原样复制、`active_constraints` 子集复制、`recent_changes` 与 episodic 重复（`memory/orchestrator.py:74-81`）；`state_export` 携带全量 `plot_threads` 与 `disambiguation_pending`（上限可至 1000 条，`config.py:208`）无截断 | 5-15k |

### 1.3 因子三：子代理串行 × 缓存 TTL 失效

每章固定 3 次子代理（context-agent / reviewer / data-agent），串行硬门槛（`SKILL.md:18-27`）+ 各次数分钟生成时间，使主代理在每次子代理返回后的首轮超过 5 分钟缓存 TTL，触发 50-100k+ 的全量 cache-miss 重读。每章约 4-6 个这样的 resume 点 ≈ **1-3M tokens**。此外三个子代理上下文彼此独立，同一批合同内容在 4 个上下文中分别读取、分别计费（子代理冷启动固定 ~10-20k）。

### 1.4 预算机制的四个「有形无实」缺口

1. `load_context(budget_tokens=4000)` 参数**无任何实现消费**（`memory_contract.py:120`、`memory_contract_adapter.py:159`，签名存在、函数体不读）；
2. `ContextManager.build_context(max_chars)` 形参**死参数**（`context_manager.py:102-118`，函数体零引用）；
3. `context_ranker.apply_budget` 只截 3 个小字段，**结构性大 section（合同/runtime_status/commit/genre_profile/memory_pack）明确豁免**（`context_ranker.py:58-93`）；genre_profile_excerpt 无字符上限（未命中题材时 fallback 取前 80 行）；
4. 章纲 1500 字按**字符硬切**（`chapter_outline_loader.py:149`），被切掉的恰是后段 CEN/禁区等关键约束；拆分章纲文件命中时**绕过上限全量返回**（`:152-154`）；`load_chapter_plot_structure` 用 `max_chars=None` 全量（`:380-382`）。

另：`data-agent` 每章必调 `index get-core-entities` **无上限全量加载**（`index_entity_mixin.py:244-256`，注释自述"全量加载"），实体数随章节线性增长，300 章后单次可达 20-50k。

### 1.5 缓存友好性

无显式 prompt-cache 设计（仓库 grep 零命中），也未发现头部时间戳/随机 ID 这类经典破坏模式；真正的敌人是 1.3 的流程节奏与 1.1 的历史膨胀。**改进原则：让稳定内容前置、大输出外置、resume 点变少。**

## 3. 外部研究给 v7 的四个可移植模式

1. **L0/L1/L2 分层加载**（OpenViking，自报输入 token ↓34%-91%）：设定/合同先给 ~200 字摘要层，命中实体再下钻原文——即两轮审计 P1-4 的「L0 摘要层」，两者互为佐证。
2. **抽取而非压缩的记忆**（Mem0/Supermemory/Zep）：存原子事实 + 矛盾消解 + 自动遗忘；对应把记忆四态中空转的 `contradicted/tentative` 做实（round2 审计 P1-3），陈旧事实及时降级出上下文本身就是省 token。
3. **大输出外置化**（OpenViking tool_output >20k 落盘 + 存根引用）：CLI 大 JSON 统一「落盘 + 一行摘要」，主对话只留结论。
4. **分阶段模型路由**（AI_NovelGenerator `choose_configs`）：提取/审查/摘要等结构化任务用便宜模型、正文用当前模型——宿主侧配置即可，不动插件代码。
