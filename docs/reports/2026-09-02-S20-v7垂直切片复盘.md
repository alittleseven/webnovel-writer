## 1. 结论摘要

1. **交付事实**：v7 写路径最小闭环（决策卡 → 上下文包 → 草稿 → 机检 → 作者验收 → settle → 原子 git commit → 缓存重建）全部走通，真书（v6）零写入。切片期间发现并修复的问题全部有测试或机制兜底（settle 原子回滚、字数契约进机检、唯一写入路径接入）。
2. **计量对比**：去缓存新增 **64.4 万 vs v6 链路 56.1 万（同量级，且 v7 侧含开发混杂）**；结构性优势显著——**子代理 0 个**（v6：4 个，155.7 万 tokens）、写作上下文 **2,691 字符 vs 17,304（−84%）**。总量指标因会话形态不可比（详见 §3 口径警告）。
3. **M3 判定：「有条件达标」**。结构性信号支持「不劣于 v6 链路」，但严格同口径计量被开发混杂污染；确认动作 = 第 38 章以独立新会话跑 v7 链路首写时补一次干净计量（列入 S21 后确认项，非阻塞）。
4. **spec 对齐收口**：S19 计划遗留的三项命名漂移（正文文件名 / front matter 键 / 散写摘要路径）经迁移仓刷新（`2389272`）已全部核销，settle 写入侧与缓存查询面均为 spec 命名；唯一尾项（`v7_write.py` 模块注释陈旧）本次顺手修正。

### 3.2 口径警告（三条，均影响解读）

1. **总量不可比**：v7 切片在跨两天的开发大会话内执行（每轮 980 万–1,773 万 tokens，≈99% 为缓存重读）；v6 链路在真实书仓的专用会话执行。总量对本次对比无意义，只看去缓存新增与结构性指标。
2. **开发混杂**：v7 写路径执行窗（09-01 23:04 → 09-02 00:03）包含四因修复（commit `98686af`）、迁移仓刷新（`2389272`）与收尾文档；v6 第 36 章是纯写作轮。**64.4 万 是"含开发混杂的上界"**，纯写路径应显著更低。
3. **返工差异**：v7 切片含一次验收打回全链返工；v6 基准未单列返工口径。
