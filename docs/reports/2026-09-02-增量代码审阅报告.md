**P1-1 迁移器名册列序错位（别名列与首现章列互换）** ✓亲验
- 证据：`scripts/migrate_v6_to_v7.py:158-165` SQL 返回序为 `(canonical_name, first_appearance, aliases)`，元组按此序存入；`:177` 消费端 `for name, aliases, first in roster_rows` 按 `(名, 别名, 首现章)` 解包 → **名册.md 的别名列填的是首现章、首现章列填的是别名串**。
- 边界讽刺：`:174` 主角保底行 `(name, "", "1")` 顺序恰好正确，掩盖了错位；测试无「index.db 含别名」用例故漏网。
- 影响：所有经 index.db 迁移的名册行两列互换；连带污染 v7_cache 单表读取的 `aliases`/`first_chapter`（`find_entity` 别名匹配失效）——S24 刚修好的双落点读取面，其单表数据源本身是错的。
- 修法：`:159` 元组改为按 `(r[0], r[2] or "", str(r[1] or ""))` 组装（或 SQL 调序），补一条带别名的迁移测试。

**P1-2 v7 连续写作缓存陈旧：settle 不刷新、损坏不自愈** ✓亲验
- 证据：settle 成功后不触发 `rebuild_cache`；`v7_cache.py:198-202` `_conn` 仅在**文件不存在**时重建。
- 影响：连续写第 N+1 章时 `pack` 的 `get_summary(N)` 查不到刚 settle 的摘要、`find_entity` 查不到新实体——上下文静默降级，直到有人手动 rebuild。指南「首查自动触发」表述失实。
- 连锁：库文件存在但损坏（零字节/半写坏，无表）时所有查询抛 `no such table` 且不触发重建，须人工删 `.cache/`——违背 spec §1.2「派生物可丢弃、首查重建」不变量。
- 修法：settle 成功尾迹调用 `rebuild_cache`；`_conn` 改为「文件缺失 **或** 健康检查失败（如 `SELECT 1 FROM meta` 失败）」时重建。

### P2 — 建议尽快处理

**P2-1 settle 防双写只查精确文件名** ✓亲验
- `v7_write.py:309-311` 只检查 `NNNN-标题.md` 精确路径存在；同章**改标题**即可二度 settle → 定稿出现两个同章号文件 → `rebuild_cache` 因 `chapters.num` 主键 + 裸 INSERT（`v7_cache.py:164-175`）抛 IntegrityError，缓存永久不可用（叠加 P1-2 的「存在即不重建」）。
- 修法：按章号前缀 `glob(f"{chapter:04d}-*.md")` 判重（与 `dual_format_guard.has_v7_settled_chapter` 的前缀扫描对齐）。

**P2-2 settle 回滚的两个缺口（S24 修复的补丁）** ✓亲验
- (a) `v7_write.py:371-373` unlink 循环未逐个 try：Windows 下文件被 AV/编辑器锁定时 unlink 抛异常会在 except 块内直接传播、**跳过 `git reset`**——留下 add 进 index 的半成品条目，恰是 S24 要消灭的中间态。
- (b) `git reset --quiet` 清的是整个 index：会把作者此前自行 staged 的无关改动一并 unstage（副作用未声明）。
- 该分支无测试（`test_v7_write.py:192-208` 用 `commit=False`，`git reset` 路径零覆盖）。

**P2-3 settle 的 git commit 无身份兜底且报错不可读** ✓亲验
- `v7_write.py:369` `_git(... "commit" ...)` 未带 `-c user.name/-c user.email`（对比迁移器 `_git_init` 有）；`_git`（:280-281）`capture_output=True` 吞掉 stderr → 无全局 git identity 的环境 settle 必败 → 回滚删章，且错误只剩 returncode。建议身份兜底 + CalledProcessError 时透出 `e.stderr`。

**P2-4 双格式守卫默认不生效** ✓亲验
- `config.py:220` `story_repo_root` 仅从 env `STORY_REPO_ROOT` 读取、默认空；迁移器 docstring 声称「建立映射」但**实际不写任何映射**（全仓 grep 仅 config 与测试引用）。v6 侧守卫只挂 prewrite 一道（precommit/postcommit 无）；v7 侧靠 decision 临时键 `v6_project_root`（`v7_write.py:304`）。两端配置默认都关——「唯一写入路径」防护实际需要人工接线。
- 修法：迁移器落一份映射（如书仓 `.webnovel/story_repo_root` 或 env 提示），precommit 补挂守卫。

**P2-5 v7_cache 对损坏输入零容错** 代理报告（与 P1-2 合并修复即可）
- `_iter_roster_directory`（`v7_cache.py:121-136`）对名册目录文件读取无异常保护：单个非 UTF-8 文件让整个 `rebuild_cache` 崩溃，单文件损坏放大为全查询面不可用。违背 spec §10 第 0 态「永不带堆栈崩溃」。

**P2-6 dashboard 无鉴权 + 数据库读写模式连接** ✓亲验
- `dashboard/server.py:46` 默认 `127.0.0.1` 尚可，但 `--host 0.0.0.0` 一个参数即把全书正文/state/合同暴露到局域网（无任何 Token）。CORS 只防浏览器跨域，不防直连。
- `app.py:314-320` `_get_db` 以默认**读写**模式连 index.db（无 `mode=ro` URI、无 busy_timeout）：违背「严格只读」定位，可能生成 -wal/-shm，写并发下 `database is locked` 直接 500。
- 修法：连接串加 `file:...?mode=ro`；绑定非回环地址时要求随机 Token（或拒绝并打印指引）。

**P2-7 v6 rejected 覆写绕过单调状态机** ✓亲验
- `state_projection_writer.py:59-65`：commit status=rejected 时**无条件**把 `chapter_status` 覆写为 `chapter_rejected`——已 committed 的章被 replay 成 rejected 时状态回退，绕过 `state_manager.py:307-313` 的单调保护。

**P2-8 H2 total_words 三路写入仍在（已知延后项，本轮补证据）** 代理报告 + grep 亲验
